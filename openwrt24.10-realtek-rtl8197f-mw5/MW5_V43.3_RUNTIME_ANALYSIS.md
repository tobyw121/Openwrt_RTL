# MW5 v43.3 runtime analysis and fix

## Evidence from the v43.2 boot log

The corrected 24-byte descriptor path is active and accepted:

- RX descriptor base is programmed.
- TX ring has 64 entries with 24-byte stride.
- `DMA_CR1=0x000005e8` and `TXRINGCR=0x00000003` read back correctly.

The external switch-to-CPU path is also working. After boot, `eth0` and the DSA
`lan` user port receive frames, while `wan` remains quiet. Therefore the switch
CPU port, RX DMA and protocol-9 RX demultiplexing are no longer the primary
fault.

The remaining runtime state is asymmetric:

- `br-lan` emits packets.
- the DSA `lan` port remains at zero transmitted packets;
- preinit opens the LAN PHY, but it is closed before procd and is not visibly
  reopened by the generated final network configuration;
- P0 still reports `cputag-tx=1`, although the Linux DSA tagger already inserts
  the complete four-byte protocol-9 tag in software.

## v43.3 changes

### 1. Separate RX parsing from TX tag generation

MW5 now keeps RTL8197F `CFG_CPUC_TAG` enabled for received CPU-tagged packets,
but clears `CFG_TX_CPUC_TAG`. The software `tag_rtl4_9` header is therefore sent
unchanged through physical P0/RGMII to the external switch. RD05 keeps its prior
hardware setting.

Expected boot marker:

```
mw5 p0 rgmii sdk: ... cputag-rx=1 cputag-tx=0 ... tag=rtl4_9/4byte
```

### 2. Complete the protocol-9 transmit tag

CPU-originated frames now set the protocol-9 disable-learning bit 9 and retain
the six-bit destination port mask.

### 3. Deterministic OpenWrt LAN/WAN topology

A board-specific uci-defaults script writes the final topology explicitly:

```
br-lan
  `- lan

wan (DHCP)
wan6 (DHCPv6)
```

The script also enables the DHCP server on `lan` and removes stale anonymous
network-device sections from earlier generated layouts.

## Runtime validation after flashing

```
dmesg | grep -E 'MW5 SDK CPU tag|mw5 p0 rgmii|txring sdk v43.3|poststart v43.3|Link is'
uci show network
uci show dhcp.lan
ip -d link show lan
bridge link show dev lan
ubus call network.interface.lan status
cat /proc/net/dev
```

Expected state:

- P0 says `cputag-rx=1 cputag-tx=0`.
- `br-lan` lists `lan` as a port.
- `lan` is administratively up and the bridge state becomes forwarding when the
  cable link is present.
- ARP/ping causes both `br-lan` and `lan` TX counters to increase.
- DHCP replies become visible on the client.

## Limitation

The source changes and patch replay have been validated, but the final result
still needs a build and hardware test on the MW5. The temporary v43.2 runtime
script can validate the register and netifd parts before flashing v43.3.

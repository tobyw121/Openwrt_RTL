# Tenda Nova MW5 / RTL8197F v43.11

## Scope

v43.11 is based directly on v43.10 and keeps the proven board topology and CPU-tag formats:

- physical LAN jack -> RTL8367 port 1 -> DSA `lan`
- physical WAN jack -> RTL8367 port 3 -> DSA `wan`
- switch CPU port -> port 6
- switch-to-CPU tag observed on LAN: `0x8899 0x0401`
- CPU-to-switch tag: LAN `0x8899 0x9202`, WAN `0x8899 0x9208`
- six-DWORD / 24-byte RTL8197FS New_swNic descriptors

The OpenWrt standard firewall remains enabled and unmodified.

## Why v43.10 still failed

The v43.10 hardware run proved that DSA RX tagging and CPU DMA are active, but the data path still failed:

- normal LAN and direct LAN/WAN all received frames but had zero DSA-port TX packets;
- direct LAN accumulated 90 oversize/bad descriptors while CPURPDCR0 advanced;
- TX submitted 82 descriptors but completed only 34 in the LAN phase;
- the same pattern repeated after the ring was rebuilt for WAN;
- CPUTPDCR0 eventually stopped advancing while Linux continued to submit descriptors.

The local RTL8197F GPL New_swNic source shows three source-level differences from v43.10.

## Fix 1: OEM CRC/FCS descriptor-length convention

The OEM driver leaves `CPUICR.EXCLUDE_CRC` clear.

RX descriptor `rx_len` includes four FCS bytes, and the OEM receive function subtracts four before delivering the frame to the network stack. TX `tx_ph_len` and `tx_mlen` include four bytes for the FCS generated by hardware.

v43.11 therefore enables `realtek,sdk-crc-lengths` for the MW5 and also forces the same policy in the MW5 runtime branch. Existing driver support then does:

- RX: `len -= ETH_FCS_LEN`
- TX: `desc_len = max(len + ETH_FCS_LEN, 64)`
- CPUICR: do not set `EXCLUDE_CRC`

The observed good descriptor length of 118 bytes is consistent with a 114-byte Ethernet+CPU-tag frame plus four-byte FCS.

## Fix 2: uncached 24-byte descriptor access

The RTL8197F SDK explicitly uses an uncached/KSEG1 descriptor view or explicit cache maintenance. This is significant on RTL8197F because its 24-byte descriptors do not align to the 32-byte MIPS cache line. The OEM TX source even documents that cached writeback can overwrite the ownership word of an adjacent descriptor.

v43.11 keeps `dma_alloc_coherent()` for allocation/free bookkeeping but accesses MW5 RX/TX descriptor slots through the KSEG1 alias derived from the ring DMA address:

```
CKSEG1ADDR(lower_32_bits(dma) & 0x1fffffff)
```

This applies to both reads and writes through the existing RX/TX descriptor accessors. Other boards retain their existing CPU pointer path.

## Fix 3: only TX ring 0 is enabled

The MW5 driver configures only:

- `CPUTPDCR0`
- the ring-0 length in `DMA_CR1`
- `DMA_CR4.TX_RING0_TAIL_AWARE`

The single-ring OEM New_swNic path does not enable additional TX rings. v43.10 nevertheless left TX ring 1 enabled, resulting in `TXRINGCR=3` while no ring-1 base/length pair was configured.

v43.11 clears TX ring enable bits 0..3 and enables only ring 0. The expected low ring-enable nibble is therefore `0x1`.

## Fix 4: match OEM TX descriptor lifetime

With `USE_SWITCH_TX_CDP`, the OEM `New_swNic_txDone()` frees the associated skb bookkeeping and advances its software done index. It does not rewrite the completed 24-byte descriptor.

v43.11 does the same on MW5:

- completed TX descriptors are left untouched until reuse;
- CPUTPDCR0 remains the completion boundary;
- start_xmit does not reject a reclaimed MW5 slot merely because the descriptor OWN bit is stale;
- software head/tail still prevents reuse of queued descriptors;
- TX EOR/WRAP is omitted for MW5 because DMA_CR1/DMA_CR4 tail-aware mode supplies the ring boundary.

This reduces writes to neighbouring 24-byte descriptor slots and removes another difference from the OEM driver.

## Diagnostics

`/proc/rd05-rtknet` now includes:

```
descriptor_policy dwords=... stride=... kseg1=... sdk_crc=... txringcr=...
```

For the MW5 v43.11 target the expected policy is:

```
dwords=6
stride=24
kseg1=1
sdk_crc=1
txringcr low enable bits = 0x1
```

`mw5-netdiag` also collects the v43.10/v43.11 `mw5 rx-bad`, RX descriptor, TX wire, TX submit and TX completion messages instead of filtering the new diagnostics out.

## Expected next hardware indicators

The most useful changes to look for after flashing are:

1. probe/register output reports `sdk-crc=1`;
2. `/proc/rd05-rtknet` reports `descriptor_policy ... sdk_crc=1 txringcr=0x00000001` (other non-enable TXRINGCR bits may be retained, but only ring0 may be enabled);
3. valid RX frame lengths are four bytes lower when delivered to Linux;
4. `oversize_drop`/`bad_desc` should fall substantially if cache-line aliasing was corrupting descriptor metadata;
5. `mw5_tx_dma complete` and `cdp_clean` should continue following `submit` instead of CPUTPDCR0 stopping after the first group of descriptors;
6. DSA `lan`/`wan` TX counters should finally increase if the corrected TX descriptor/FCS policy allows the frames to reach the external switch.

## Deliberately unchanged

- LAN/WAN DSA mapping
- RTL8367 CPU-port mapping
- RX `0x0400 + source port` decoder
- TX protocol-9 DSA tag construction
- RGMII TX/RX delays
- OpenWrt standard firewall configuration

## Validation limitation

This source revision is statically validated and patch-replayed, but it has not been cross-built with the user's MIPS/OpenWrt toolchain or executed on the physical MW5 in this environment. Hardware success must be confirmed by the next `mw5-netdiag` run.

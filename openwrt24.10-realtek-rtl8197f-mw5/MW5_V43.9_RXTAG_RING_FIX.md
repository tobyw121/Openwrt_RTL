# Tenda Nova MW5 v43.9 RX-tag / ring-completion correction

This tree targets Tenda Nova MW5 with RTL8197F/RTL8197FS and the external
RTL8367-family switch. The hardware-proven mapping remains unchanged:

- physical LAN jack -> RTL8367 port 1 -> DSA `lan`
- physical WAN jack -> RTL8367 port 3 -> DSA `wan`
- RTL8367 CPU port -> port 6 -> RTL8197F P0/RGMII

The standard OpenWrt firewall4 configuration introduced again in v43.8 is
retained unchanged.

## v43.8 hardware evidence

v43.8 finally preserved a real switch-to-CPU tag in the RTL8197F RX buffer.
The first captured LAN frame contains:

    DA | SA | 88 99 | 04 01 | 86 dd | payload ...

The RTL8197F descriptor for that frame also reported external source metadata
for physical LAN port 1. The v43.8 `rtl4_9` decoder nevertheless rejected the
frame as `unknown protocol=0x0` because it incorrectly interpreted the RX tag
with the CPU-to-switch TX bit layout.

The same log proves that Linux TX reaches the master immediately before DMA as:

    DA | SA | 88 99 | 92 02 | EtherType | payload ...

for DSA LAN port 1. Therefore the two directions are asymmetric on this
hardware and must not share one 16-bit tag-word decoder.

Only `0x0401` from physical LAN port 1 is directly proven by the v43.8 raw
capture. A raw WAN `0x0403` was not captured in that run. v43.9 therefore does
not hard-code WAN to a single whole tag word; it decodes the low six source-port
bits generically after recognizing the observed `0x0400` switch-to-CPU marker.

## DSA tagger correction

`tag_rtl4_9.c` now uses separate layouts.

CPU -> switch TX remains:

    EtherType 0x8899
    protocol[15:12] = 9
    disable-learning = bit 9
    destination mask = bits [5:0]

For LAN port 1 the current encoded tag is `0x9202` because the destination is a
one-hot mask (`BIT(1)`).

Switch -> CPU RX now first recognizes:

    (tag & GENMASK(15,10)) == BIT(10)   /* observed 0x0400 marker */
    source port = tag & GENMASK(5,0)

Thus the proven `0x0401` frame is delivered to DSA port 1 instead of being
rejected as protocol zero. A protocol-9 compatibility decoder remains as a
fallback for older/synthetic SDK paths.

## RTL8197F descriptor fallback

The preferred path is now real 0x8899 wire pass-through. If a valid external
MW5 frame arrives without 0x8899, the master may still reconstruct a tag from
the descriptor source-port field. For safety this fallback remains limited to
the hardware-proven physical ports 1 and 3.

Unlike v43.8, the fallback constructs the switch-to-CPU layout:

    0x8899 | (0x0400 | source_port)

rather than a CPU-to-switch protocol-9 word.

## RX completion correction

v43.8 still accumulated large `bad_desc`/`oversize_drop` counts. Some alleged
descriptor words even contained byte patterns resembling Ethernet/IP payload,
which is consistent with software observing a descriptor before DMA had
finished updating it or with stale/corrupted descriptor state.

Earlier bring-up code allowed CPURPDCR0 advancement to override an OWN bit that
was still set. v43.9 changes MW5 so:

- descriptor OWN is the authoritative completion indication;
- CPURPDCR0 is retained only as a diagnostic cursor;
- if OWN remains set, RX polling stops at that descriptor even if CDP advanced;
- `mw5_rx_own_wait` counts those observations;
- every recycled descriptor has its `addr` rewritten from the software-owned
  `rx_dma[idx]` mapping before OWN is returned to hardware;
- address mismatches are counted and bounded descriptor snapshots are logged.

This is deliberately conservative: it avoids consuming a slot whose DMA
ownership has not been returned to the CPU.

## TX completion instrumentation

v43.8 proved the correct DSA-tagged bytes exist before `dma_map_single()`, but
user-port TX remained zero. v43.9 therefore adds bounded traces around the next
boundary:

- `mw5 tx-submit v43.9`: descriptor index/DMA address, mapped packet DMA,
  opts1..opts5, CPUTPDCR0 before/after the kick and OWN after kick;
- `mw5 tx-complete v43.9`: descriptor completion after hardware clears OWN;
- `/proc/rd05-rtknet` exposes submit/completion/OWN-after-kick counters.

This does not claim that physical egress is fixed yet; it makes the DMA -> P0
boundary measurable on the next hardware run.

## Automatic test readiness

The v43.8 capture showed the automatic test could be started before normal
OpenWrt network initialization had completed, while the temporary random master
MAC was still visible and `br-lan` did not yet exist. v43.9 `mw5-netdiag` waits
up to 90 seconds for `br-lan` and an `up` LAN interface from netifd before it
records the original state and starts the normal-LAN test.

## Firewall

No diagnostic firewall bypass is present. v43.9 keeps the normal OpenWrt
firewall configuration, normal LAN/WAN zones, NAT/forwarding defaults, and the
v43.8 first-boot migration helper for users upgrading from the old v43.7
no-firewall image.

## Test after flashing

Run over serial console:

    mw5-netdiag

The most important new evidence is:

    rtl4_9 v43.9 RX layout=s2c-0400 ...
    mw5 rxdesc v43.9: ...
    mw5 tx-submit v43.9: ...
    mw5 tx-complete v43.9: ...
    cat /proc/rd05-rtknet

A successful RX correction should show `rtl4_9 v43.9 RX layout=s2c-0400` and
DSA `lan`/`wan` RX frames reaching the corresponding Linux slave. TX diagnosis
should show whether every submit receives an OWN-cleared completion and how
CPUTPDCR0 advances.
